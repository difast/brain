# Агент устройства

Программа, которая играет роль **тела**: запускается на ноутбуке, по сети
разговаривает с мозгом на сервере, исполняет присланные команды и отчитывается
о результате.

Робота нет — а разговор настоящий: настоящий сервер, настоящая сеть, настоящий
SDK, настоящие решения.

```bash
cd device
pip install -r requirements.txt

# Ключ организации из панели: Аккаунт → Разработчику
MEVRATEK_API_KEY=cbk_… python run.py --task "найди бутылку"
```

## Зачем это

**Проверить, что мозг действительно думает.** Если провайдер модели не
настроен или отвечает с ошибкой, платформа возвращает заготовленную заглушку.
Устройство при этом работает, дашборд зелёный, ошибок нет — и отличить одно от
другого снаружи невозможно. Агент считает долю заглушки и говорит её вслух в
конце каждого прогона.

**Показать платформу вживую.** Ноутбук, веб-камера, на экране живые решения по
реальной картинке.

**Дать пример интеграции.** То, что копирует инженер заказчика, когда
подключает своё устройство.

## Устройство папки

Одна программа ведёт разговор, и есть сменная деталь, которая физически
исполняет команды. Программа не знает, какая деталь вставлена.

```
run.py                  запуск и разбор аргументов
mevratek_device/
  agent.py              цикл — не меняется при смене железа
  hardware.py           форма разъёма: что обязана уметь любая деталь
  simulated.py          деталь №1 — виртуальный ровер
  camera.py             глаза: нет / файл / веб-камера
  identity.py           токен устройства между запусками
  console.py            вывод в терминал
tests/                  32 теста
```

`hardware.py` требует ровно двух вещей: «расскажи, что умеешь» и «выполни вот
это». Поэтому настоящее железо — это **новый файл**, а не переписывание: в нём
вместо `print("еду вперёд")` будет напряжение на моторы.

## Как запускать

```bash
# по датчикам, без картинки — так работает робот-доставщик
python run.py --camera none --task "объезжай препятствия"

# картинка из файла: подменяйте файл на ходу, следующее решение увидит новое
python run.py --camera file --frame scene.jpg --task "подъедь к зелёному предмету"

# веб-камера — это и есть демо
pip install opencv-python
python run.py --camera webcam --task "опиши, что видишь, и подъедь к предмету"

# задачи из очереди платформы, а не из --task:
# оператор ставит задачу в панели, устройство её разбирает
python run.py --pull-tasks

# конечный прогон для замеров
python run.py --rounds 50 --interval 2
```

Против боевого сервера:

```bash
MEVRATEK_API=https://api.mevratek.ru/api/v1 MEVRATEK_API_KEY=cbk_… python run.py
```

Всё, что задаётся флагом, можно положить в `config.yaml` — скопируйте
`config.example.yaml`. Файл в `.gitignore`: в нём ключ.

## Что происходит за один круг

```
читаем датчики        → POST /telemetry
берём кадр            ─┐
                       ├→ POST /brain/decision   {task, state, image_b64}
задача                ─┘
исполняем команды     → железо
отчитываемся          → POST /executions        {action_id, status, error}
```

Последний шаг — самый важный и самый недооценённый. Отчёт попадает в память
мозга и показывается модели на следующем круге. Именно поэтому провалившийся
манёвр не повторяется вслепую.

## Устройство помнит, кто оно

После первой регистрации токен сохраняется в `.device-state.json` и
переиспользуется. Так ведёт себя настоящее устройство: регистрируется один раз
за жизнь.

Без этого каждый запуск создавал бы в панели новое устройство, терял очередь
задач (задачи адресованы конкретному устройству) и обнулял историю решений,
которая и есть память мозга.

Начать с чистого листа: `python run.py --fresh`.

## Как читать вывод

```
[3] батарея 97.2% · до препятствия 1.2 м · кадр 41 КБ
    → вижу бутылку справа на столе, беру правее
      yandexgpt · уверенность 0.87 · 1.2 с
    ✓ turn_right 15    повернул направо на 15°
    ✗ move_forward 0.5 упёрся в препятствие
```

`⚠ claude:fallback` вместо имени модели означает, что решение приняла заглушка.
Если так во всех строках — модель не подключена, и всё, что вы видите, это
работа заранее написанного кода, а не мозга.

`! N действ. отброшено` означает, что модель попросила то, чего это устройство
не умеет. Платформа такие команды не пропускает. Единичные — норма, постоянные
— проблема с промптом или со словарём действий.

## Про симулятор

Это **не физический движок**. Трение и инерция не моделируются — проверяется
разговор, а не механика.

Что моделируется, потому что без этого разговор становится неинтересным:
батарея садится, стена приближается, и часть команд проваливается сама по себе.
Последнее важнее всего: устройство, у которого всё всегда получается, никогда
не задействует обратную связь, а обратная связь — это ровно то, что не
проверено.

## Тесты

```bash
python -m pytest device/tests -q
```

Тестируется то, что имеет свою логику: ровер и хранение токена. Ценность
`agent.py` доказывается **запуском против живого сервера**, а не моками: смысл
этого файла именно в том, что он работает по настоящей сети. Отдельно покрыты
случаи, которые трудно воспроизвести по требованию — обрыв связи, отброшенные
действия, подсчёт доли заглушки.

## Известный пробел в протоколе

Устройство не узнаёт, что задача выполнена. В ответе мозга нет такого признака:
есть цель, мысль, уверенность и действия — но нет «готово». Поэтому взятая из
очереди задача остаётся в статусе «в работе».

Это не недоделка агента, а недостающая часть протокола. Всплыло при написании
этой папки — что само по себе довод в её пользу.

## Настоящее железо

Появится файл `raspberry.py` с тем же разъёмом. Меняется одна строка запуска:

```bash
python run.py --hardware raspberry --camera webcam
```

`agent.py`, `identity.py`, `console.py` и весь разговор с сервером остаются
прежними.
